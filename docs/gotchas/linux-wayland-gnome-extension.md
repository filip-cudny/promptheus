# GNOME Wayland — shortcuts, positioning and focus through the GNOME Shell extension

## Rule

On GNOME Wayland, Promptheus runs as a native Wayland client. Wayland has no protocol for global shortcuts, window positioning or window activation by a client, and `tauri-plugin-global-shortcut` only grabs keys through XWayland (they arrive while an X11 window has focus). Everything that needs the compositor goes through the GNOME Shell extension `promptheus@promptheus.desktop` (`linux/gnome-shell-extension/`), reached over the session D-Bus by `src-tauri/src/services/gnome_shell/`. Do not add `setPosition`, `set_focus()` or plugin shortcut code for this path.

## Why

- The extension runs inside the compositor: it can grab accelerators, read the pointer and the monitor work area, move and activate a window, and read the focused window's `wm_class`.
- `org.gnome.Shell.Eval` is blocked since GNOME 41.
- Backend selection (`services/gnome_shell::is_gnome_wayland`): `XDG_SESSION_TYPE=wayland` and `XDG_CURRENT_DESKTOP` contains `GNOME` → extension backend, always. Anything else (macOS, other desktops) → `tauri-plugin-global-shortcut` and the old placement path. Without the enabled extension on GNOME Wayland there are no shortcuts (`warn` log) and the context menu opens only from the tray, at the old, wrong position (`shell_placement: false`).

## D-Bus contract

Interface `com.promptheus.Shell`, object `/com/promptheus/Shell`, served by `org.gnome.Shell`:

| `GetPointer` | `() → (iiiiii)` | pointer x, y, then work area x, y, width, height of the monitor under the pointer |
| `PlaceWindow` | `(s title, i x, i y, b activate) → b` | move the window with that title, optionally activate it |

| `GetFocusedWmClass` | `() → s` | `wm_class` of the focused window |

| `UpdateRecordingWidgetRetry` | `(u attempt, u max_attempts, u delay_ms) → ()` | switch the pill to `retrying`: row 1 shows "Retry `attempt`/`max_attempts` in S s" counting down from `delay_ms`, then a wave; always rebuilds row 1 (a repeated call restarts the countdown); throws when no widget is shown |

| `HideRecordingWidget` | `() → ()` | remove the widget |
| `RestoreAppWindow` | `(s wm_class) → s` | finds the main window of `wm_class` (same test as `PasteIntoApp`: type `NORMAL`, no transient parent) and answers `absent` (none), `shown` (not minimized and already `global.display.focus_window`, nothing activated), `restored` (was minimized or not focused, also on another workspace: `Main.activateWindow`, which switches to it, then waits up to `RESTORE_TIMEOUT_MS` 2000 until it is not minimized and is `global.display.focus_window`) or `restore_timeout` (that wait timed out); logs `RestoreAppWindow: <state>` and, for an activated window, `RestoreAppWindow: minimized|unfocused, restore wait <ms> ms`; never the title |
| `WatchAppTitles` | `(s wm_class, u duration_ms) → ()` | returns at once; for `duration_ms` logs (journal, `console.log`) every title change of the main windows of `wm_class` (existing at the call, and windows created during the watch once their WM class matches) as `WatchAppTitles: title change window <id> +<ms> ms`, plus `start (<n> windows)`, `window <id> created +<ms> ms` and `end`; never the title; a new call or `disable()` ends a running watch |
| `CaptureArea` | `(s path, s owner) → s` | hide the pill and the owner window, let the user drag a screen rectangle, write it as PNG to `path`, show them again; `captured` or `cancelled`; `owner` is `""` for the pill, else the exact title of the owner window (see "CaptureArea" below) |
| `CaptureSelection` | `(s owner) → (s outcome, s text)` | wait for text the user selects in another app after the call (`captured` with the text, `cancelled`); `owner` as in `CaptureArea`; one wait at a time (see "CaptureSelection" below) |
| `CancelCapture` | `(s owner) → b` | end the running selection wait of `owner` with `cancelled`; `true` when a wait of that owner ran, `false` otherwise |
| `ShortcutActivated` | signal `s action` | an accelerator fired |
| `RecordingWidgetAction` | signal `s action` | widget button pressed: `pause`, `resume`, `stop`, `cancel`, `paste`, `screenshot`, `select_text` or `stop_chat`; `cancel` also stops a running transcription retry |
| `RecordingWidgetTargetSelected` | signal `s id` | a dropdown row was clicked |

| `RecordingWidgetMoved` | signal `(i x, i y, i work_x, i work_y, i work_width, i work_height)` | drag released after the pointer moved more than 4 px: pill origin and the work area of the monitor it was dropped on, logical stage pixels |
| `Ready` | signal | the extension is enabled and serving |

## Pattern

Lifecycle:
- The extension emits `Ready()` in `enable()` and after unlock (extensions are disabled on the lock screen).
- Rust calls `SetShortcuts` again after every `Ready`, so shortcuts survive unlock and an app started before the extension was enabled.
- The extension watches the bus name of the `SetShortcuts` caller and ungrabs its accelerators when the name vanishes (app exit or crash), so the keys return to the focused app.
- Shortcuts are grabbed for the normal and overview action modes only: they do not fire on the lock screen.
- Accelerators come from `get_active_bindings` converted by `to_gtk_accelerator` in `services/hotkeys.rs`. An accelerator GNOME already uses is returned by `SetShortcuts` and logged at `warn`; the other shortcuts keep working.

Window identification:
- Windows are found by title. The context menu title is `CONTEXT_MENU_TITLE` (`commands/menu.rs`), the notification title is `NOTIFICATION_TITLE` (`services/notification_window.rs`); both are set in `setup/windows.rs`, as are `PROVIDER_MENU_TITLE` (`commands/provider_menu.rs`), `PALETTE_TITLE` and `PALETTE_BACKDROP_TITLE` (`services/ai_webview/palette.rs`). `IMAGE_PREVIEW_TITLE` (`commands/image_preview.rs`) is the image-preview title. Change a title only in its constant.
- The overlay titles in `extension.js` (`OVERLAY_TITLES`) must equal the Rust constants byte for byte; renaming a title constant needs the same edit in `extension.js`.
- For overlay typing and `ActivateWindow` the extension matches its own windows by WM class `promptheus` (the binary name), never by title alone: titles such as "Settings" and "History" collide with other apps.
- Any process on the session bus can call `PlaceWindow` and `SetShortcuts`; there is no caller check.

Dock icon and overlays:
- GTK3 sends no skip-taskbar hint on Wayland, so every mapped overlay is a normal toplevel and shows a dock icon. The extension sets `Meta.WindowType.UTILITY` on each window of WM class `promptheus` whose title is in `OVERLAY_TITLES`; the dock and Alt+Tab then skip it.
- The type is set per map: GTK3 destroys the surface on `hide()`, so every show is a new `MetaWindow`. The extension handles `window-created`, the windows that exist at `enable()` (after unlock), and a title or WM class that arrives after creation (`notify::title`, `notify::wm-class`); the watch is dropped after the first match, on `unmanaged` and in `disable()`.
- The six overlay titles: `CONTEXT_MENU_TITLE`, `PALETTE_TITLE`, `PALETTE_BACKDROP_TITLE`, `PROVIDER_MENU_TITLE`, `NOTIFICATION_TITLE`, `IMAGE_PREVIEW_TITLE`.
- The image-preview window is activated by the extension right after it is typed (`Main.activateWindow`); `set_focus()` on a mapped window is denied by Mutter. The other overlays get no activation from this path.
- Regular windows (chat, settings, history, context editor, text previews) are never typed and keep the dock icon.
- Neither the typing path nor `ActivateWindow` logs a window title: text-preview titles hold user text.
- A second `ActivateWindow` for the same title while one waits finishes the first with `false`; `disable()` finishes every waiting call with `false`.

Context menu placement:
- GTK3 on Wayland creates the surface at `show()`, so the window does not exist for Mutter before it.
- `gnome_shell::place_window(title, x, y, activate, Some(win))` puts the `PlaceWindow` call on the bus before `win.show()` and then awaits the reply. The extension waits up to 1000 ms for the window, keeps its compositor actor hidden (`opacity = 0`) until the first frame, then, in a `Meta.LaterType.BEFORE_REDRAW` later, moves it, activates it when `activate` is set, and shows it. The wait ends with `false` when the window is unmanaged before that. With `None` it only sends `PlaceWindow` to an already visible window. `place_context_menu_through_shell` calls it with `activate = first`.
- A second `PlaceWindow` for the same title while the first still waits cancels the first (it returns `false`, logged at `warn`) and is handled on its own.
- Pitfall: placing or activating the window inside the actor's `first-frame` handler crashed GNOME Shell 50.1 (SIGABRT, `invalidate_top_window_actor_for_views: assertion failed: (!priv->frame_in_progress)`; GNOME then disables user extensions). `first-frame` is emitted while Mutter paints a frame, and any restack (`Main.activateWindow`, `make_above`) aborts there. Every restack from a paint-time signal goes through a `BEFORE_REDRAW` later.
- GTK `set_opacity` cannot do this: it has no effect on Wayland.
- `GetPointer` supplies the cursor and work area; the frontend positions inside the work area and calls `place_context_menu` (see `src/lib/components/features/context-menu/DOCS.md`).
- Constant window height: the window is sized at open for the menu with the recent list open (closed menu + list block, the block measured by a hidden probe), and the list toggle never calls `setSize` or `place_context_menu`. A native resize on the toggle cut the list on expand and blanked the menu top on collapse (`docs/analyses/context-menu-list-toggle-flicker.md`).
- Offset: the closed menu is drawn at `margin-top` = `closedOffset` (the shift `clamp_menu_origin` applied to the window, within the list block), 0 after an expand, so it stays at the pointer without moving the window.
- Input region: the transparent strip around the menu must not take clicks, so the frontend sends `set_context_menu_input_region` (the bounding rectangle of the menu and open submenus) before `place_context_menu`, after every toggle, offset change and submenu open/close; Rust re-applies it after every show.

Host-relative popups:
- A window placed relative to a host gets the host as transient parent (`gnome_shell::set_transient_parent`, on the GTK main thread, on every open because the windows are shared by all hosts) and is placed with `place_window_on_parent`.
- The provider menu window (title `PROVIDER_MENU_TITLE`, unchanged) is one generic popup: it shows whatever `items` the `provider-menu:show` payload carries, serving the provider switcher and the strip's `+` and `+N` lists.
- Provider menu offset is `(rect.left, rect.bottom + 4)` window-relative; palette and backdrop offset is `(0, TOOLBAR_HEIGHT)`, size host width × (H − 40), so the toolbar stays undimmed and clickable.
- Without the extension the transient parent alone makes Mutter place them over the host.
- On GNOME Wayland the shell animates the transient provider menu as `DIALOG` (`scale_y` 0↔1, 100 ms, pivot at the middle); the extension's `connect_after` handlers on `global.window_manager` `map` and `destroy` move the pivot to `(0.5, 0)` for the window titled `Promptheus Provider Menu`, so it unfolds from and folds into its trigger. This relies on the shell setting its pivot synchronously before the ease starts (GNOME Shell 50.1); other transient windows (palette, backdrop) keep the center pivot.

Notification toasts:
- On GNOME Wayland `services/notification_window.rs::show_notification` calls `ShowToast` (async, proxy method `show_toast`) and does not touch the webview queue. The extension draws the toast as St actors in `Main.layoutManager.uiGroup`: not windows, never focused, non-reactive (no hover pause) unless the payload has an `action`: then a click emits the `ToastActivated(s action)` signal (the app listens in `setup/shortcuts.rs` and runs `open_settings_window` for `open_settings`) and hides the toast.
- Durations are set in the extension (`TOAST_DURATIONS_MS`: success 2000, error 4000, info 2000, warning 3000 ms). The stack sits bottom-right in the work area of the monitor current when the stack went from empty to non-empty, newest at the bottom.
- Each toast actor eases in and out with the values of GNOME Shell's window map/destroy animation for normal windows (`windowManager.js` `_mapWindow`/`_destroyWindow`): enter from pivot (0.5, 1.0), scale 0.01 × 0.05, opacity 0 to scale 1 and opacity 204 in 150 ms `EASE_OUT_EXPO`; exit at pivot (0.5, 0.5) to scale 0.8 and opacity 0 in 150 ms `EASE_OUT_QUAD`, after which the actor is destroyed and the remaining toasts move to their new place without animation.
- A failed `ShowToast` call logs `warn` and shows that payload through the webview window path below. That path is also the only one on macOS.
- Why actors: Mutter ignores the GTK3 `accept_focus` hint (`focusable(false)`) for Wayland clients and focuses the mapped notification window anyway, even with `activate=false`; focus returns only when `hide()` unmanages it.

Recording widget:
- Drawn by the extension as a reactive St actor added with `Main.layoutManager.addTopChrome` (unlike the non-reactive toasts, it receives clicks above windows): no modal (`Main.pushModal`), no `global.stage.grab`, so the client keeps keyboard focus. Buttons are `St.Button` children; dragging the pill body is handled in the shell (a `captured-event` handler on the stage for the duration of the drag).
- Drag: `button-press-event` on the pill installs a stage `captured-event` handler; it moves the pill only after the pointer moved more than `WIDGET_DRAG_THRESHOLD_PX` (4 px) from the press point, and only then stops the release and emits `RecordingWidgetMoved`. A press whose event actor (`global.stage.get_event_actor(event)`) is an `St.Button` or inside one never starts a drag.
- Pitfall: a stage `captured-event` handler sees events before every actor. When it returned `Clutter.EVENT_STOP` for the `BUTTON_RELEASE` of a press that started on a child `St.Button` (the press bubbles to the pill), the button never got the release and never emitted `clicked`; each click only logged `recording widget dragged to X,Y`. Any stage capture handler must propagate events it does not own.
- Pitfall: the `BUTTON_RELEASE` of a drag does not always reach the stage `captured-event` handler; the handler then stayed connected and every later motion moved the pill with no button held. A `MOTION` without `Clutter.ModifierType.BUTTON1_MASK` in `e.get_state()` ends the drag the same way as the release (disconnect, `RecordingWidgetMoved` if the pill moved).
- Level bars: every bar is a fixed `WIDGET_BAR_MAX_HEIGHT` (28 px) actor with `pivot_point` (0.5, 0.5), vertically centred in a row of the same height, and the level is shown through `scale_y`, a transform: sub-pixel, and it changes no allocation, so the bar row is not relaid out per frame. On each `UpdateRecordingWidget` in `recording`, `_easeWidgetBars` computes each bar's target scale (`WIDGET_BAR_MIN_SCALE + (1 − WIDGET_BAR_MIN_SCALE) · level · WIDGET_BAR_FACTORS[i]`, `WIDGET_BAR_MIN_SCALE = 4 / 28`, no rounding), skips bars whose target differs from the last one (`widget.scales[i]`) by less than `WIDGET_BAR_SCALE_EPSILON` (0.005), and calls `bar.ease({scale_y, duration: WIDGET_BAR_EASE_MS (60), mode: LINEAR})`. Updates arrive every 50 ms; a new `ease` replaces the running transition and starts from the current scale, so a linear ease about one update interval long joins the segments at a near-constant speed. Earlier versions animated `height` with a 100 ms `EASE_OUT_QUAD`: each restart every 50 ms began at the curve's highest speed (a velocity jump 20 times a second), and `height` rounds to whole pixels and relays out the row every frame, both visible as a slight tremor. Clutter computes the intermediate frames on the stage frame clock, so JS runs only on the 20 Hz updates and no timer is needed. No `onStopped`/`onComplete` callback is used (see the unmapped-actor pitfall below); on a bar not yet mapped `ease` just sets the scale. Every state change goes through `_clearWidgetContent`, which calls `remove_all_transitions()` on each bar before `destroy_all_children`; `paused` rebuilds the bars at the last target scales and keeps them still. Cost of the transform: the 2 px `border-radius` is squashed with the bar, so the ends of short bars are nearly square.
- Layout: the pill is a vertical box of three rows, `WIDGET_WIDTH` 264 × `WIDGET_HEIGHT` 72 (equal to `PILL_WIDTH`/`PILL_HEIGHT` in `widget.rs`; the GNOME pill and the webview pill look and behave the same: a change goes to both in the same change and only platform-forced differences are allowed; layout in `src-tauri/src/services/speech/DOCS.md` "macOS layout and dropdown"), radius 16: items row (`widgetItemsHeight(item_rows)`, visible only while items exist; an `St.ScrollView` with overlay scrollbar and vertical scrolling around a vertical `St.BoxLayout` of line `St.BoxLayout`s: image chips first, as wide as their content, `WIDGET_IMAGE_COLUMNS` (3) per line, then each text chip on its own 236 px line, so the lines fill the `min(ceil(images / 3) + texts, 3)` rows the backend reserved and scroll beyond 3; no `+N` chip; chip form and thumbnail (`image_path` as a 20 × 20 `background-image`, `background-size: cover`) in `src-tauri/src/services/speech/DOCS.md` "macOS layout and dropdown"); row 1 (state content below; in `recording`/`paused`: level bars, time, then a right-aligned group (`_widgetActions`, spacing 4) of Pause/Resume, Cancel (`cancel`; icon swapped to `recording-cancel-hover.svg` while hovered), Finish (`stop`; `recording-arrow-up.svg` on a `#e5e5e7` circle)), row 2 (before the target lock in `recording`/`paused`/`processing`: target button with selected label and a static `recording-chevrons-up-down.svg`, then a right-aligned group of Paste (`paste`) and stop + chat (`stop_chat`); the row's left padding is 6 px so the label text lines up with the bars; after the lock and in `done`: the same row, label in place, the chevron and the buttons faded out and non-reactive, see `src-tauri/src/services/speech/DOCS.md` "macOS layout and dropdown"). Row 1 is an `St.Widget` with `Clutter.BinLayout` so outgoing and incoming state content overlap during the crossfade ("Transitions" there). Hovering a chip for 300 ms (`WIDGET_PREVIEW_DELAY_MS`) shows a popover: text in a wrapping `St.Label` up to 160 px high, with a bottom fade when it does not fit, or an image thumbnail in a fixed 264 × 160 `St.Widget` with CSS `background-image: url("file://…")` (a small PNG written by the backend, because St decodes `background-image` synchronously in the compositor and a full screenshot would stall the shell; a file and not base64 over D-Bus, to avoid Cogl texture code in GJS). The popover is a non-reactive actor in `Main.layoutManager.uiGroup` (like the toasts) so it never takes the hover from the chip; it sits at the pill's x, above or below like the dropdown with a 6 px gap, and is destroyed on leave, refill, drag start, dropdown open and pill removal. Row height, gap, padding and max rows equal those in `widget.rs`. Rows grow upward because the backend keeps the bottom edge. A model arriving before the first `UpdateRecordingWidgetModel` renders as empty (label `Dictation`, no items).
- Dropdown: a separate `St.BoxLayout` added with `Main.layoutManager.addTopChrome` (never `pushModal`/grab/focus), same x and width as the pill, above it when the pill centre is in the lower half of its monitor's work area, else below; one click-only row per target, the selected one bold. Closes on selection (after `RecordingWidgetTargetSelected`), a second click on the target button, drag start, a model with `target_locked` or state `done`, and pill removal (`_removeRecordingWidget` calls `removeChrome` + `destroy`, so `disable()` and the sender-vanish callback remove it too). A model update while it is open reopens it at the new position. Chips and buttons never start a drag (`_isInWidgetButton`).
- States: `recording`/`paused` show the level bars, the elapsed time and the buttons; `processing` shows only a wave of `WIDGET_WAVE_BAR_COUNT` bars (computed from `WIDGET_WIDTH`, `WIDGET_PADDING_X`, `WIDGET_WAVE_BAR_WIDTH` 2 and `WIDGET_BAR_SPACING` 3: 47) at opacity 150, visible heights `WIDGET_BAR_MIN_HEIGHT + WIDGET_WAVE_HEIGHT / 3 · (0.5 + 0.5 · sin(phase − i · 2π / count))` (4..12 px, `WIDGET_WAVE_HEIGHT` 24, set as `scale_y` = height / `WIDGET_WAVE_HEIGHT` on the same bar builder with a 24 px bar), phase from `GLib.get_monotonic_time()` with a 1.2 s period; `done` shows the check icon and "Copied"; `retrying` shows the text "Retry N/M in S s" and the Cancel button (`cancel`, right-aligned like in `recording`), counted down by one `GLib.timeout_add` stored in `widget.retryId` that fires at each whole-second change of the remaining time (from `widget.retry.endUs`, monotonic µs) and is removed by `_clearWidgetContent`; at 0 the timer rebuilds row 1 with a wave of `WIDGET_RETRY_WAVE_BAR_COUNT` bars (40, the width left of the Cancel button) on the same `waveId` timer and phase as `processing`. The wave runs on one `GLib.timeout_add` (33 ms) stored in `widget.waveId`; `_clearWidgetContent` removes it before `destroy_all_children`, and `_removeRecordingWidget` and `disable()` go through `_clearWidgetContent`.
- Pitfall: GNOME Shell's `actor.ease()` on an actor that is not mapped (for example a child of a box not yet added to the stage) creates no transition and calls `onStopped(true)` synchronously (`environment.js` copies Clutter's skip of implicit transitions for unmapped actors). The former processing spinner restarted its `ease` from `onStopped` while the icon's box was not yet added to the pill, so it recursed until `InternalError: too much recursion`; `UpdateRecordingWidget` threw before `add_child`, the pill stayed empty during processing, and the floating content was finalized, so the stored `widget.spinner` wrapper pointed at a disposed `St.Icon` and the transition to `done` logged `Object St.Icon (0x…), has been already disposed`. Do not loop an animation through `onStopped`; drive repeated animations with a timer (or a `Clutter.Timeline`) owned by the widget, and remove it before destroying its actors.
- `ShowRecordingWidget` position is validated by the shell against the current monitors; outside every work area (or `has_position = false`) it uses the default, bottom center 24 px above the work area bottom of the pointer's monitor.
- Hidden by `HideRecordingWidget`, when the bus name of the `SetShortcuts` caller vanishes, and in `disable()`.
- Pitfall: Mutter's direct scanout (`find_candidate` in `meta-compositor-view-native.c`) puts the top window's buffer straight on the output when that window covers the whole monitor, without checking shell actors above windows; on a monitor without the top panel a maximized window covers it, so the pill and the toasts flickered or vanished there. GNOME Shell's own overlays (`osdWindow.js`, `messageTray.js`, `boxpointer.js`) call `global.compositor.disable_unredirect()` while shown; Mutter counts the calls and each needs exactly one `enable_unredirect()`. The extension disables once when `ShowRecordingWidget` builds the pill and enables once in `_removeRecordingWidget` (every hide path, `disable()` included); toasts disable when the stack goes from empty to non-empty and enable when `_removeToast` empties it or `_clearToasts` clears a non-empty stack. The dropdown and the chip preview live only while the pill exists and need no call of their own. Platform-forced difference: GNOME-only compositor workaround, nothing in `App.svelte` (the macOS compositor draws the webview pill as a normal window).
- Rust side: `services/speech/widget.rs` (see `src-tauri/src/services/speech/DOCS.md`); position stored under `recording_widget.shell_position`. A failed `ShowRecordingWidget` makes the recording use toasts.

Notification placement (webview window path):
- `services/notification_window.rs` reads `GetPointer` and sends `PlaceWindowAnchored(NOTIFICATION_TITLE, work_right, work_bottom, activate=false)` before the first `show()`, with the bottom-right corner of the work area under the pointer. The window is `focusable(false)`, which Mutter does not honor for Wayland clients (see above).
- The extension sets the frame to x = `right` − frame width, y = `bottom` − frame height from `get_frame_rect()`. It applies this at placement (after `first-frame` when it had to wait for the window), once more on the next idle, and on every `size-changed` of the `MetaWindow`. It moves only when the computed x/y differ from the current frame position, so its own move does not re-trigger it.
- The anchor is stored per title; a new `PlaceWindowAnchored` for the same title replaces it. It is released on the window's `unmanaged` signal: GTK3 on Wayland destroys the surface on `hide()`, so each show cycle is a new `MetaWindow` and a new `PlaceWindowAnchored`.
- `.always_on_top(true)` in `setup/windows.rs` maps to GTK `keep_above`, which has no Wayland protocol under GTK3 (`xdg-shell` has no stacking request); on Wayland it does nothing.
- The extension calls `make_above()` in `_anchorWindow` on every anchor, so the window stacks above app windows; every window placed with `PlaceWindowAnchored` is kept above. The window is `focusable(false)`; without `make_above` Mutter stacks it as a normal never-focused window under the focused app, and an occluded surface gets no frame callbacks (resize answered 20–30 s late).
- `update_notification_window` on the extension path only calls `set_size`; the extension follows the resize. The macOS path keeps `set_position` then `set_size`. `anchor_and_show` calls `set_size` (380 × `FIRST_SHOW_HEIGHT`) before showing, because after `hide()` the GTK window keeps its size from the previous cycle.
- Why the anchor lives in the extension: the GTK client commits a new size asynchronously. A top-left computed in Rust from the requested height reached Mutter before or after the real resize, so the frame kept the old height at the new origin or the new height at the old origin, and the toast stack (anchored to the window bottom by Sonner `position="bottom-right"`) ended below the work area. Resizing before `PlaceWindow` did not fix it. Only the compositor knows the real frame size.
- The notification drain closes every toast still live `DURATIONS[level] + 1500` ms after it showed (own timer per toast plus a sweep at the start of every `drainPending`) and logs a `warn` with the source (`timer`/`sweep`) and page state, because sonner timers have been seen to stall on GNOME Wayland (cause not yet known).
- A toast paused under the pointer is closed the same way and also logs the `warn`.
- The drain logs at `debug` the toast show/close lines (close with path `autoClose`/`dismiss`/`watchdog`), toaster mouse/pointer events, window focus/blur/keydown (`altKey` and whether the code is `KeyT` only, never the key) and `visibilitychange`; kept in the product for diagnosing a future stall.
- `update_notification_window` logs at `debug` the toast count, requested logical height and either the extension anchor (bottom-right) or the computed origin.
- `GetPointer` coordinates are logical stage pixels, so the shell anchor uses scale 1.0; the macOS path keeps physical pixels and `set_position`.
- If the extension call fails (extension disabled), the show path logs at `warn` and falls back to `cursor_position` + `find_monitor_at` + `set_position`; Mutter ignores the position and places the toast itself.
- `services/monitor.rs::find_monitor_at` falls back to the monitor under the cursor, then `primary_monitor()`, then the first of `available_monitors()`. On Wayland `cursor_position()` is not global and GDK reports no primary monitor; without the last fallback the notification never showed (`no monitor found`).

Install:
- `.deb`: `bundle.linux.deb.files` in `src-tauri/tauri.conf.json` installs `metadata.json`, `extension.js` and the icons into `/usr/share/gnome-shell/extensions/promptheus@promptheus.desktop/`, one entry per file: a new file in `icons/` must get its own entry, or the installed extension draws no icon (the dev symlink from `install-dev.sh` hides the omission).
- Development: `linux/gnome-shell-extension/install-dev.sh` symlinks the directory into `~/.local/share/gnome-shell/extensions/`.
- Then re-login and `gnome-extensions enable promptheus@promptheus.desktop`. The app never installs or enables the extension itself.
- `metadata.json` `shell-version` lists exact GNOME majors (`["50"]`); add the new major on each GNOME release.
- A changed `extension.js` needs a re-login: GNOME Shell caches loaded ES modules, so `gnome-extensions disable`/`enable` re-runs the old code.

Debugging:
- `gdbus introspect --session --dest org.gnome.Shell --object-path /com/promptheus/Shell` — 13 methods, 6 signals when the extension is enabled.
- `gdbus monitor --session --dest org.gnome.Shell` — watch `Ready` and `ShortcutActivated`.
- `journalctl --user /usr/bin/gnome-shell` — extension errors.
- `journalctl --user -f -o cat /usr/bin/gnome-shell | grep Promptheus` — host-relative placement: `Promptheus: place on parent "<title>" parent=X,Y frame=X,Y WxH`; anchored placement lines: `Promptheus: make_above "<title>"` on every anchor, then `Promptheus: anchor "<title>" right=R bottom=B moved=… frame=X,Y WxH`, then `re-anchor after placement` and `re-anchor on size-changed` with the same fields, and `anchor released "<title>"` on hide. A correct anchor has `X + W = R` and `Y + H = B`.

## PasteIntoApp (Claude Desktop paste)

`PasteIntoApp(s wm_class, as uris) → s outcome` focuses the app's main window (the first window of the WM class with type `Meta.WindowType.NORMAL` and no transient parent, so never a dialog), pastes the file list with Ctrl+V and sends Return. Outcomes: `sent`, `no_window`, `focus_lost` (never `no_read`, which only macOS produces).

Steps:
1. Poll every 100 ms up to 20 s for that main window; none → `no_window`. A window absent at the first poll marks the run cold.
2. `Main.activateWindow`, wait up to 2 s for `global.display.focus_window` to be exactly that window; else `focus_lost`. Every later focus check compares the same way, so a Claude dialog holding focus (e.g. its hardware acceleration notice after a cold start) gives `focus_lost`; a check by WM class let Ctrl+V go into the dialog, Return press its default button, and reported `sent`.
3. Cold only: settle 4000 ms. A warm run has no settle here: the caller (`claude_desktop::linux::open_link`) already waited for the `claude://` handler to exit plus its own settle.
4. With `uris`: save one clipboard type (`text/plain;charset=utf-8`, else the first `image/*`; `Meta.Selection.transfer_async` into a `Gio.MemoryOutputStream`; a failed read saves nothing), own the clipboard with a `Meta.SelectionSourceMemory` holding only `text/uri-list`, focus check, one Ctrl+V, a fixed 1000 ms wait.
5. Focus check, Return.
6. With a saved type and `sent`: 500 ms after Return own the clipboard with a `Meta.SelectionSourceMemory` of the saved bytes (nothing saved → the file list stays). `focus_lost` after the clipboard was taken leaves the file list, no restore.

Why the shell owns the clipboard: on Wayland the unfocused Promptheus cannot own a selection (no focus, no serial), the shell can.

Why the built-in `Meta.SelectionSourceMemory` and not a `Meta.SelectionSource` subclass: GJS cannot override a vfunc that takes a callback. A class with `vfunc_read_async(mimetype, cancellable, callback)` throws `VFunc read_async accepts another callback as a parameter. This is not supported` at `GObject.registerClass`, i.e. at module load, so the whole extension fails and `/com/promptheus/Shell` is never exported (all shortcuts dead). The cost: no read signal, so no paste confirmation (a fixed delay; Claude Desktop reads `text/uri-list` at Ctrl+V and its message waits for the uploads), and one mimetype per source, so the restore puts back one type and the other saved formats are lost. The log carries the outcome, cold/warm and whether the clipboard was restored, never URIs or content.

Step log lines, each with `+<ms> ms` since the method's entry (`PasteIntoApp: <step> +<ms> ms`): `window found (warm|cold)` (cold: the +ms is the wait), `focused`, `settle done` (cold only), `files pasted, Ctrl+V sent (<n> URIs)`, `Return sent`, `clipboard restored`, then the `outcome` line. They exist to compare against the `WatchAppTitles` lines (same journal) when picking a signal that Claude handled the `claude://` link.

Why `RestoreAppWindow` runs before the `claude://` handler: a minimized Claude restored by the handler's second instance leaves the text unsent in the composer (keyboard focus does not reach it; live runs 2026-11-06, Return 1968–1992 ms after the link, outcome logged `sent`). The extension restores and focuses the window first, so the hand-off wait starts with a shown window; a window that does not come back within 2 s ends in `Timeout` (no handler, no paste, no Return). A Claude window without focus (e.g. behind another window, or on another workspace, which `Main.activateWindow` switches to) is activated the same way: the handler's second instance shows Claude's main window without an activation token, so GNOME refuses it focus and shows its "“Claude” is ready" attention notification on every delivery (live, 2026-11-06); an activated, focused window gets no such notification.

An extension without the method (not re-logged in after an update) answers `UnknownMethod`; Rust treats the error as `Failed` and falls back to the clipboard and a toast. For `RestoreAppWindow` Rust treats the error as an absent window (cold path).

## CaptureArea

`CaptureArea(s path, s owner) → s outcome` (`captured`, `cancelled`; an exception is a D-Bus error `com.promptheus.Shell.Error`). The backend calls it on a fresh proxy with no widget lock held, so the call lasts as long as the selection. `owner` names the window the capture was started from: `""` is the pill, any other value is the exact title of a window (the context menu, the chat host window).

Steps:
1. Close the pill's dropdown, chip preview and tooltip, hide the pill actor. For a window owner, resolve the window once with `_findWindow(owner)` and keep the `Meta.Window` (the chat title changes with the active tab, so the title is never looked up again); remember whether it is `global.display.focus_window`, then `hide()` its actor (`win.get_compositor_private()`, no unmap, no move). A title that matches no window captures without hiding one.
2. A reactive `St.Widget` over the whole stage (`global.stage` size, all monitors), `rgba(0, 0, 0, 0.4)`, crosshair cursor (`set_cursor_type(Clutter.CursorType.CROSSHAIR)`, gone with the actor), `Main.pushModal(overlay)` for pointer and keyboard. Press and drag draw a translucent outlined rectangle, release finishes. Esc or a right click cancels; a rectangle under 4 px on a side cancels. A selection may span monitors.
3. `Main.popModal(grab)`, destroy the overlay, wait 100 ms (`CAPTURE_FRAME_WAIT_MS`, a fixed wait after the redraw the destroy queues, so the overlay is not in the image; stops being correct below 10 Hz refresh), then `Shell.Screenshot.screenshot_area(x, y, w, h, stream)` into `Gio.File.replace` of `path`, stream closed.
4. In every outcome (captured, cancelled, error) `show()` the owner window actor again and, when it was focused, `Main.activateWindow(win)`; show the current `this._widget?.actor`, never the actor taken at the start: `HideRecordingWidget` during the selection destroys it and a new `ShowRecordingWidget` may build another.

The coordinates are stage coordinates in logical pixels, passed unscaled; `screenshot_area` takes `gint32`. Source checked: GNOME Shell 50.1 `ScreenshotAreaAsync` (`screenshot.js`) validates the area against `global.screen_width` x `global.screen_height`, which are stage-sized. The PNG resolution on a scaled monitor is chosen by Shell (not read from any source here; the live run on a scaled monitor decides it). The same `ScreenshotAreaAsync` multiplies the caller's area by `St.ThemeContext.get_for_stage(global.stage).scale_factor` before the check; if the live run on a scaled monitor shows a wrong area, apply that factor in `_writeAreaPng`. The log carries whether the owner is the pill or a window, the outcome and the rectangle size; never the owner title (the chat title holds user text).

## CaptureSelection

`CaptureSelection(s owner) → (s outcome, s text)` (`captured`, `cancelled`). `owner` is `""` for the pill, else the exact title of the owner window (context menu, chat host window). The backend calls it on a fresh proxy with no widget lock held, so the call lasts until a selection arrives or a cancel path resolves it. The extension receives no input events of other apps' surfaces (Mutter stops them before the stage), so it watches the PRIMARY and CLIPBOARD selections instead.

Steps:
1. `this._selection = {owner, win, finish}` is the one wait slot of the whole extension, shared by all owners (`null` in `enable()`, finished with `cancelled` in `disable()`); a new call of any owner resolves the running wait as `cancelled` first (one capture at a time), a pill wait included, and then redraws row 2 when the new owner is not the pill and the pill exists, so it leaves `Select text…`. A window owner is resolved once with `_findWindow(owner)` and kept in `win` (never looked up again, the chat title changes with the active tab); no window found answers `cancelled` at once, without ending a running wait. It runs with or without the pill. For owner `""` row 2 is rebuilt: label `Select text…`, no chevron, the select-text button keeps the hover background; a window owner's wait does not touch the pill. For owner `""` without a pill the call answers `cancelled` at once.
2. `global.display.get_selection()` `owner-changed` with `Meta.SelectionType.SELECTION_PRIMARY` or `SELECTION_CLIPBOARD` (apps that copy on select and set no PRIMARY, e.g. herdr via OSC 52) and a source whose `get_mimetypes()` contains `text/plain;charset=utf-8`, `text/plain`, `UTF8_STRING`, `STRING` or `TEXT`. A CLIPBOARD change counts only inside a mouse gesture: from the start of the wait a `GLib.timeout_add` polls `global.get_pointer()` every 30 ms (`SELECTION_POLL_MS`), records whether a `BUTTON1_MASK` press began outside the owner (`pointInRect` with `widget.actor` for the pill, so the select-text click and other presses on the pill never open the window; with `win.get_frame_rect()` for a window owner, read at each press because the window may move) and the release time; the change counts while that press is held or up to 500 ms (`SELECTION_GESTURE_WINDOW_MS`) after its release, otherwise it is ignored (logged) and the wait goes on. PRIMARY changes need no gesture. For a window owner an `owner-changed` (either type) while `global.display.focus_window === win` is ignored (logged as `owner window focused, ignored`, no title), so text selected in the menu filter or the chat composer is never taken.
3. Poll `global.get_pointer()` every 30 ms (`SELECTION_POLL_MS`) until `BUTTON1_MASK` and `SHIFT_MASK` are both up (the selection is final after the drag or Shift+arrow ends), wait 150 ms (`SELECTION_SETTLE_MS`), read `St.Clipboard.get_default().get_text(…)` with the type that changed (`St.ClipboardType.PRIMARY` or `CLIPBOARD`).
4. Null or empty text keeps waiting for the next `owner-changed`; otherwise `finish('captured', text)`.

Cancel paths, each resolving `cancelled` exactly once (`finish` is idempotent, disconnects the `owner-changed` handler, removes the gesture poll and the release poll or settle timeout, clears `this._selection` when it is this slot and redraws the pill's row 2 only on `captured` of a pill wait; the cancel paths redraw themselves, because `_fillRow2` calls `finish`): `CancelCapture(owner)` for the wait of that owner (`false` when none runs; for `""` it redraws row 2 afterwards), a new `CaptureSelection` of any owner, `disable()`, and the pill paths below, which read and cancel only a pill wait (`this._selection` with `owner === ""`); a window owner's wait running while the pill shows leaves the pill's row 2 and buttons as they are. The pill paths: a click on the select-text button while waiting (resolved locally, no action emitted), a click on the target label while waiting (opens no dropdown), `ShowRecordingWidget` (reuses the widget), `_removeRecordingWidget` (also from `disable()`), and `_fillRow2` building a non-interactive row (target lock through `UpdateRecordingWidgetModel`, state `done`). zbus sets no method timeout, so an unresolved call would leave the Rust task pending forever. There is no Esc and no timeout. The log carries the selection type that changed, the outcome and the text length only, never the owner title.

An interface change (the `owner` arguments, `CancelCapture`) needs a log out and in to load the new extension, see "A changed `extension.js` needs a re-login" above; an old extension answers `UnknownMethod` or an argument error.

Accepted limits: a GTK entry claims PRIMARY again on focus-in (Alt+Tab after the click), which counts as a selection when its text is non-empty; a CLIPBOARD write that is not a selection is taken as the selection when it lands while button 1 is held for a press outside the pill or within 500 ms of its release (a background write by an app, a backend clipboard write of this app, the `PasteIntoApp` restore or Mutter's clipboard-manager takeover on an app exit, during a drag); the owner-changed source names no client, so only the writers this app controls could be told apart; apps that set neither PRIMARY nor CLIPBOARD on select (canvas apps) cannot be captured. Inferred from Mutter and GTK source; the live run confirms it.
