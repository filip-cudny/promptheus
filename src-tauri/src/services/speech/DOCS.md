# Speech service

Recording, transcription, and the retry path that keeps a failed voice note recoverable.

## Failure model

`SpeechError::Transcription` carries a `FailureKind`:

- **Transient** — 408, 429, 5xx, connect failures, timeouts, unparseable responses. Re-sent automatically.
- **Permanent** — 401/403, 4xx request rejections, missing API key, no speech detected. Never re-sent.

`retry.rs` runs at most `surfaces.speech_to_text.auto_retry_attempts` attempts (default 3, `1` disables retrying) with exponential backoff — 2s, 6s, 18s, capped at 60s, ±20% jitter. A numeric `Retry-After` header overrides the computed delay. Every intermediate failure emits `speech-transcription-retry`.

`transcribe_with_retry` takes an async callback (`on_retry`) that the loop awaits when an attempt fails and another is left, before the backoff starts. The automatic path uses it to report each failure in the pill or a toast, so a retry is reported when its attempt fails, not after the loop.

An optional abort (`watch::Receiver<bool>`) ends the loop with `SpeechError::Cancelled` (message `Cancelled`). It is checked before each attempt and raced against the request and the backoff sleep; a `true` aborts. A dropped sender never aborts. The automatic path passes an abort; a manual retry passes none and cannot be cancelled.

The HTTP timeout scales with payload size (`30s + bytes / 50 kB/s`, capped at 300s). A fixed ceiling turned slow uplinks into self-inflicted timeouts on multi-minute recordings.

## Audio clips

A recording is written to `audio_clips/<uuid>.wav` under the app data dir before the first transcription attempt, with a row in `audio_clips` (schema v6) holding the path, duration, and `expires_at`. Retention is `surfaces.speech_to_text.audio_retention_hours` (default 3, `0` disables storage entirely).

Lifecycle:

- **Success** — clip deleted immediately, unless `keep_audio_on_success` is set, in which case it is attached to the new history entry.
- **Failure** — a history entry is created with `success = false` and the clip is attached to it. This is the anchor for "Retry transcription" and "Export audio".
- **Cancelled recording** — Cancel while recording or paused keeps the samples: they are encoded and stored as a clip, and a failed entry "Voice note · m:ss — cancelled" (error `Cancelled`) holds it, so "Retry transcription" transcribes it later. Nothing is kept (no entry, no toast) when `audio_retention_hours` is `0`, the recording is shorter than `MIN_RECORDING_SAMPLES_SECS`, or encoding or storing the clip fails. The retention is read from the settings directly, so a missing STT model does not drop the audio.
- **Cancelled retry** — Cancel during an automatic retry creates the same failed entry with the clip attached, as the final failure does.
- **Expiry** — `spawn_audio_clip_sweeper` runs every 15 minutes (plus once at startup) and drops expired rows with their files.
- **Orphans** — the same sweep deletes any `.wav` no row points at. This is what reclaims clips lost to `ON DELETE CASCADE`, history retention pruning, and `clear()`; there is no file cleanup in the delete paths themselves.

Clips are on disk rather than in memory deliberately: a transcription usually fails because the network or the provider is down, and the user may well quit the app before trying again.

## Retry concurrency

`is_transcribing` guards the freshly recorded audio only. Manual retries use `SpeechService::begin_retry` / `end_retry`, a per-entry-id set, so replaying an hour-old clip never blocks a new recording and two retries of the same entry cannot overlap.

A manual retry **updates the history entry and the clipboard, and never pastes**. By the time someone retries, the app that had focus during dictation is long gone — pasting into whatever happens to be focused now would be worse than useless. For the same reason a retry does not re-run a pending skill, even if the original recording was started as "run skill with transcription".

A new recording stays blocked while an automatic retry runs: `is_transcribing` stays set until the loop ends or is cancelled.

`SpeechService::retry_abort` holds the abort sender of the running automatic transcription. It is armed in the callback of the first reported failure (so only a run that is retrying can be aborted) and disarmed after the loop returns. Before the first failure it is `None`. A composer transcription arms it when it starts and `release_composer` clears it.

Nothing is retried automatically at startup. Failed entries with a live clip wait for a click, which keeps the lifecycle free of a replay queue and avoids a burst of requests when the machine comes back online.

## Commands

The recording state machine lives in `session.rs`; `commands/speech.rs` wraps it (the audio-clip, recording-state and keyterms commands live there directly). `toggle_speech_recording` starts and stops (on stop it runs the retry loop in a background task); `cancel_speech_recording` has two branches: with `retry_abort` armed it only fires the abort (the transcription task then handles `SpeechError::Cancelled`), otherwise a recording or paused session is cancelled keeping its audio (ignored when not recording or while transcribing); `retry_transcription` spawns a background retry, drives the UI through events and returns immediately; `export_audio_clip` copies the WAV to a caller-supplied destination (the frontend picks it via `plugin-dialog`); `discard_audio_clip` deletes a clip before expiry. `get_audio_clip_info` returns `has_audio`, `expires_at`, `duration_secs`, `bytes` and `is_retrying` for one entry.

## Events

| Event | Payload | Emitted when |
|-------|---------|--------------|
| `speech-recording-started` | `{ action_id }` | Recording begins |
| `speech-recording-stopped` | `{ had_audio }` | Recording ends, before transcription |
| `recording-widget-state` | `{ state, level, elapsedMs, monochromatic }`, plus `attempt`, `maxAttempts`, `delayMs` when `state` is `retrying` | Every widget update (`state`: `recording`/`paused`/`processing`/`retrying`/`done`, `level` 0..1; `attempt` is the attempt about to run, `delayMs` the backoff before it); sent to the `recording-widget` window only |
| `speech-transcription-retry` | `{ attempt, max_attempts, next_in_secs, reason, entry_id }` | Each transient failure; `attempt: 0` marks the start of a manual retry |
| `speech-transcription-complete` | `{ text, duration_secs, entry_id }` | Success (or a discarded too-short recording) |
| `speech-transcription-error` | `{ message, recoverable, entry_id, has_audio, attempts }` | Attempts exhausted, a permanent failure, or a cancelled automatic retry (`message` `Cancelled`, `recoverable` = `has_audio`) |
| `dictation-busy-changed` | `null` or `{ by: "pill" \| "chat" \| "settings" }` | After every change of the busy state (see "Composer dictation"); app-wide, not a `speech-*` event |
| `composer-dictation-level` | `{ tabId, level, elapsedMs }` | Every 50 ms while a composer records; owner window only |
| `composer-dictation-transcribing` | `{ tabId }` | A composer transcription starts (also a retry); owner window only |
| `composer-dictation-transcript` | `{ tabId, text }` | Success, or an empty `text` for a too-short or silent recording; owner window only |
| `composer-dictation-error` | `{ tabId, message }` | A composer transcription failed, its WAV is held for Retry; owner window only |
| `composer-dictation-cancelled` | `{ tabId }` | A composer recording or transcription was cancelled (command or owner end); owner window only |

Cancel of a recording emits `speech-recording-stopped` and then `speech-transcription-complete` with empty `text`, like a discarded too-short recording; when the audio is kept it also emits `history-changed` for the new entry and, when the pill was not shown, shows the toast "Recording cancelled — audio kept, transcribe from the menu".

Cancel of a retry emits no `speech-recording-stopped`; its `speech-transcription-error` follows `history-changed` and the toast (see "Recording widget").

`entry_id` is `null` for the automatic path when no history entry was created (pending-skill executions, no-speech results).

## Recording widget

Convention: the window pill (`src/windows/recording-widget/App.svelte`) and the GNOME Shell extension pill (`linux/gnome-shell-extension/promptheus@promptheus.desktop/extension.js`) look and behave the same (width, button order, icons, colours, gaps, hover, animations). A change to one pill's look or behaviour is made to both in the same change; only platform-forced differences are allowed and are listed under "macOS layout and dropdown".

`widget.rs` (`RecordingWidget`) is called from `session.rs` at every transition, so one place owns widget state and the setting check. Setting: `surfaces.speech_to_text.show_recording_widget`, default `true`; off keeps the toast-only behavior.

`appearance.icons` (`mono` default, shared with the notification icons): `mono` draws the "Copied" check of the `done` state in the widget foreground (`#e5e5e7`), `color` in green (`#62A878`). Read in `show()` with `show_recording_widget`, so a change applies from the next recording. GNOME: 4th argument of `ShowRecordingWidget`, the extension picks `icons/recording-check-mono.svg` or `icons/recording-check.svg`. macOS: `monochromatic` field of every `recording-widget-state` payload.

- **Transports** — GNOME Wayland: the extension draws the widget (`ShowRecordingWidget` / `UpdateRecordingWidget` / `HideRecordingWidget`, see [linux-wayland-gnome-extension.md](../../../../docs/gotchas/linux-wayland-gnome-extension.md)). macOS: webview window `recording-widget` (`src/windows/recording-widget/`) fed by `recording-widget-state`. The `retrying` state goes through its own call: GNOME `UpdateRecordingWidgetRetry(attempt, max_attempts, delay_ms)` (`update_recording_widget_retry`; `UpdateRecordingWidget` rejects `retrying`), macOS the `recording-widget-state` payload with `attempt`, `maxAttempts`, `delayMs`; `push` picks the call by the state. Any other Wayland session, or a failed `ShowRecordingWidget`, falls back to toasts for that recording with a `warn` log. On macOS the `recording-widget` window is re-classed at setup into the non-activating `NSPanel` subclass `PromptheusWidgetPanel` (`canBecomeKeyWindow`/`canBecomeMainWindow` NO, `hidesOnDeactivate` NO, `services/macos_panel.rs`), because a click on a plain `NSWindow` of an inactive app activates the app and the frontmost app stops receiving keystrokes; it is shown and hidden with tauri `show()`/`hide()`, never `show_panel_without_activating`. The `recording-widget-overlay` window is re-classed into the same panel class (see "Overlay slot").
- **Toasts** — while the widget is shown it replaces "Recording started", "Processing audio" and "Speech transcribed". Error and warning toasts and the reminder stay. A retry is reported in the pill, with no toast, while it is shown. Without the pill (setting off, fallback) each failure that leaves another attempt shows the warning toast "Retrying transcription" ("Attempt N of M failed — retrying in Ss"), once per failure; the final "Speech transcribed" toast then reads "Processed in X.Xs, attempt N of M" (without the attempt count when the first attempt succeeded). There is no toast after the loop. A cancel from the pill shows no toast, the pill closing is the confirmation. Without the pill a cancelled recording with kept audio shows the info toast "Recording cancelled — audio kept, transcribe from the menu" and a cancelled retry "Transcription stopped — audio kept, retry from the menu" ("Transcription stopped" when no clip is attached). A cancelled retry never shows a "Transcription error" toast.
- **Transitions** — `recording` ⇄ `paused` → `processing` → `done` (about 1 s, "Copied"), then closed. A failed attempt with another left moves `processing` → `retrying` (`retrying_if_current`, allowed only from `processing` or `retrying`) and each further failure re-enters `retrying` with the new values; a success after a retry goes `retrying` → `processing` (`processing_if_current`) → `done` or closed as above. X in `retrying` (action `cancel`) fires the abort, the `SpeechError::Cancelled` arm of the transcription task then closes the pill. The arm runs in this order: failed entry with the clip, `history-changed`, `close_if_current`, pending prompt cleared, info toast, `set_transcribing(false)`, `speech-transcription-error`. `retrying_if_current`, `processing_if_current` and `close_if_current` follow the generation guard below. `processing` shows only a dimmed wave of 2 px bars with 3 px gaps (the level meter's gap) across the inner width of the pill, travelling left to right once per 1.2 s: no buttons, no timer, no label. Bar count on both pills `floor((width − 2 × 14 + gap) / (bar + gap))` = 47. GNOME: driven by one `GLib.timeout_add` (33 ms), opacity 150. macOS: a staggered CSS `@keyframes` `scaleY` animation, color `#929294` instead of opacity. Closed without `done`: start failure (the recorder thread reports a stream build or play error, `start_recording` fails and the pill is never shown), too-short recording, encode or runtime/API-key error, transcription error, cancel, no speech detected. A pending skill closes the widget right after processing, with no `done`. The `done` row-1 content (check + "Copied") enters once with scale 0.85 → 1 and opacity 0 → 1, 180 ms, ease-out cubic, pivot at the centre; webview: CSS `@keyframes`, off under `prefers-reduced-motion: reduce`; GNOME: `ease` with `EASE_OUT_CUBIC` after the content is added to row 1. Row 1 content swaps into `processing`, `retrying` and `done` crossfade in 150 ms, ease-out cubic: the old content fades out, non-clickable, while the new one fades in over it (`done` enters with its own scale ease above instead of the fade-in); `recording` ⇄ `paused`, a repeated `retrying`, the retry countdown → retry wave switch and every swap into `recording` stay instant. Webview: row 1 is a one-cell grid, each state's content a `.layer` in the same cell, Svelte `fade` with `cubicOut` (`swap`; duration 0 under `prefersReducedMotion`), outgoing layers are `inert`. GNOME: row 1 is an `St.Widget` with `Clutter.BinLayout`; `_clearWidgetContent(widget, true)` makes the last content non-reactive and eases it to opacity 0, leftovers are destroyed by the next `_clearWidgetContent`; the outgoing wave stops moving during the fade (its timer belongs to the widget).
- **Retrying** — row 1 shows the countdown text "Retry N/M in S s" (N the attempt about to run, S the whole seconds left, rounded up) at the left and the Cancel `X` at the right edge, in the 28 px action group. The renderer counts down from `delayMs` received once, with a timer that wakes at each whole-second change (GNOME: `widget.retryId`, a `GLib.timeout_add`; macOS: `setTimeout`). At 0 it replaces the text by a wave of 40 bars (`WIDGET_RETRY_WAVE_BAR_COUNT` / `RETRY_WAVE_BAR_COUNT` = `floor((264 − 2 × 14 − 28 − 10 + 3) / (2 + 3))`, the width left of the X, 2 px bars, 3 px gaps) travelling with the `processing` wave's 1.2 s period, while the attempt runs. The backend pushes nothing at 0, so the switch drifts from the backend's sleep by the D-Bus or event latency (milliseconds). Row 2 is unchanged: the target stays selectable (not locked); a cancel drops the pending target, so a later "Retry transcription" only copies the text. A new `retrying` push restarts the countdown.
- **Pause** — `is_recording` stays `true`; the cpal callback drops samples while paused and the microphone stays open (the OS indicator stays on); `SpeechService::elapsed()` excludes paused time; the reminder skips paused ticks and shifts its timers by the pause length. Stop from pause transcribes. In `paused` the meter bars hold the last level and are dimmed.
- **Level** — a session-scoped task every 50 ms computes the RMS of the new buffer tail (`reminder::rms`) and sends a level on a dB scale with state and elapsed time, awaiting each update before the next tick. `level_from_rms`: `dbfs = 20·log10(rms / 32768)`, level = `clamp((dbfs − FLOOR_DB) / (CEIL_DB − FLOOR_DB), 0, 1)` with `FLOOR_DB = −50`, `CEIL_DB = −20` (RMS ≈ 104 → 0, ≈ 1036 → 0.67, ≥ 3277 → 1). A linear `rms / 6000` kept normal speech (RMS 500–3000) at 0.1–0.4, so the bars looked flat. The mapped level then goes through `smooth_level`, an envelope follower stepped once per tick: `level += (target − level) · rate` with `LEVEL_ATTACK = 0.6` when the target is higher and `LEVEL_RELEASE = 0.2` when it is lower, so a rise reaches 60 % of the step in 50 ms and a fall from 1 to silence takes about 11 ticks (550 ms) to drop below 0.1. The smoothed value starts at 0 per session and is reset to 0 while paused. Rendering interpolates between the 20 Hz updates: GNOME calls Clutter `ease` on each bar's `scale_y` (a transform: sub-pixel, no relayout) with a 60 ms `LINEAR` ease, about one update interval, so successive segments join at a near-constant speed; the earlier 100 ms `EASE_OUT_QUAD` on `height` restarted at its highest speed every 50 ms and rounded to whole pixels, which showed as a slight tremor. Clutter computes the intermediate frames on the frame clock and JS runs only on the 20 Hz updates (see [linux-wayland-gnome-extension.md](../../../../docs/gotchas/linux-wayland-gnome-extension.md)); macOS bars are `transform: scaleY(…)` with `transition: transform 120ms ease-out`.

- **Overlay slot (dropdown, preview and tooltip)** — the three overlays are shown in a second window, `recording-widget-overlay` (`OVERLAY_WINDOW_LABEL`, page `recording-widget-overlay.html`, `src/windows/recording-widget-overlay/`), never in the pill window, so no overlay changes the pill frame. `setup/windows.rs` builds it like the pill: transparent, no decorations, no shadow, not focusable, accept first mouse, always on top, skip taskbar, hidden at creation; on macOS it is re-classed into `PromptheusWidgetPanel` and gets its own pointer tracking (see "Pointer on macOS"). One slot `inner.overlay: Option<Overlay { kind: Dropdown|Preview|Tooltip, up, height, seq, shown }>` holds at most one overlay (`height` physical px; `seq` from `inner.overlay_seq`, incremented on every open; `shown` true once the page's render was acknowledged); pure `next_overlay(current, request)` returns the new overlay and the kind it closed: opening one kind replaces another and reports it closed, closing a kind that is not current changes nothing. Frame: `overlay_frame(pill_origin, pill_size, frame_height, up, work_area)` — width = pill width (264 × scale), height `PREVIEW_FRAME_HEIGHT` 166 (popover max 160 + gap 6) for the preview, `TOOLTIP_FRAME_HEIGHT` 30 (tooltip 24 + gap 6) for the tooltip, `dropdown_height(rows, separator)` = (`rows` × 28 + 2 × 4 + 9 with a separator) for the dropdown (`DROPDOWN_ROW_HEIGHT`, `DROPDOWN_PADDING`, `DROPDOWN_SEPARATOR_HEIGHT`), all in logical px × scale; above the pill (bottom edge at the pill's top edge) when `dropdown_opens_up` (pill centre in the lower half of the work area), else below (top edge at the pill's bottom edge); then `clamp_origin` into the work area. The 6 px gap is inside the height of the preview and tooltip (a margin in the page), the dropdown has none and touches the pill. The pill window is not resized or moved for an overlay; its frame changes only for item rows, a drag and show/hide.
- **Overlay open and ack** — `Inner::begin_overlay(kind, logical_height)` (window transport with a placement, else an error) increments `seq`, computes the frame from the pill's `Placement` and returns `OverlayPlan { seq, up, frame, step, replaced }`. `step` is `OverlayStep::InPlace` when the current overlay is shown with the same kind, side and height (the content is replaced by the descriptor, no frame change, the window stays visible), else `OverlayStep::Reframe { hide }` with `hide` true when the current overlay is shown. A `Reframe` sets the frame through `apply_overlay_frame` while the window is hidden (macOS: at alpha 0, see below), never through `apply_frame` or `programmatic_origin`, so it produces no `Moved` for the pill. The backend then emits the descriptor event `recording-widget-overlay` to the overlay window: `{ seq, kind: "dropdown"|"preview"|"tooltip", up, index?, text?, centerX? }` (`index` and `text` for the preview, `text` and `centerX` for the tooltip, centre in pill CSS px). The page renders it and, after `tick()` (for an image also `img.decode()`) and two `requestAnimationFrame` callbacks, if the descriptor is still the current one, calls `recording_widget_overlay_rendered(seq)`. `finish_overlay(seq)` accepts only the current overlay that is not yet shown: a close or a newer open makes the ack stale (`debug` log `stale overlay ack`) and the window is not shown for it. `open_overlay` holds the widget lock only to plan, set the frame and emit; it does not wait for the ack, and the ack command takes the lock itself, so a close or a newer open between the descriptor and the ack is never blocked. The page keeps the descriptor unproxied (`$state.raw`), so it compares it by identity.

- **Overlay show path** — hidden + show does not guarantee a fresh first frame, so the show path differs by platform. macOS (`macos_panel::prepare_overlay_frame` / `reveal_overlay_panel` / `conceal_overlay_panel`, each one `run_on_main_thread` closure): the window stays ordered in; a `Reframe` sets alpha 0 and click-through (`setIgnoresMouseEvents(true)`), sets the frame with `setFrame:display:` (the computation of `set_frame_physical`, shared) and orders the window in (`orderFrontRegardless`) when it is not visible, all in one closure, so the frame and the content change with nothing on screen; `InPlace` changes no frame and leaves alpha 1. After the ack, sent two animation frames after the DOM update (the window is ordered in at alpha 0, so frames run and the second one runs after the new content was painted), `reveal_overlay_window` raises alpha to 1 and clears click-through. Every close only conceals (alpha 0, click-through, window still ordered in); the pill hiding (`close_locked`) and `hide_for_capture` also order the window out (`order_out_overlay`, `window.hide()`), so no ordered-in overlay window remains without a pill. `RecordingWidget::overlay_visible()` is true after a successful reveal and false on every conceal and order-out; it replaces `is_visible()` as "shown" (an alpha-0 window is visible to the OS). Other platforms keep hidden + show: a `Reframe` hides a shown window (`conceal_overlay_window` → `window.hide()`), sets size and position (`set_size` + `set_position`), and the ack shows it (`window.show()`); no X11 path is designed or checked. `debug` logs: `overlay reveal seq=…`, `overlay conceal`, no user text. Measurement (macOS, build `88e072c` in dev `pnpm tauri dev` and in release `pnpm bundle:mac`, binary from the bundle): `screencapture -v -C` of the full screen (60 fps time base, a new frame on each screen change), two text items in the pill; per cycle hover item A 1.0 s, leave 0.5 s, hover item B 1.0 s, click the target label (dropdown), click again; 3 cycles; frames extracted with `ffmpeg -fps_mode passthrough`, mean luminance per frame of the overlay and pill areas, transitions checked by eye. Result of hidden + show: the first frame of preview B was clean (release 3/3 overlays below the pill, dev 3/3 above); the first frame of the dropdown after a preview was stale in release 1/3 and in dev 1/2 (one frame, about 17 ms, showing the preview's text at the dropdown frame, then the list); the pill flickered in no frame of either run. Mechanism: the window was hidden with the preview's content, its frame changed while hidden, and on show the compositor drew the old backing store for one frame. This led to the alpha 0 path above; it was not re-measured. Not measured: below one 60 fps frame; release with overlays above the pill.

## Composer dictation

The main chat (`conversation-dialog`) and the settings agent (`settings-dialog`) record and transcribe speech as their own session: no pill, no toast, no reminder, no audio clip, no history entry, no clipboard write, no `speech-*` event. The flow is `composer.rs`; it reaches the outside only through the `ComposerEffects` trait (emit to the owner window, app-wide busy state, transcribe), implemented by `AppEffects` and by a fake in the tests, and it never touches the widget, notifications, clips, history or the clipboard.

- **Owner** — `SpeechService` records who owns the session: `Pill` or `Composer(ComposerOwner { label, tab_id })`, `label` the calling webview (`ComposerOwner::new` accepts only the two labels above), `tab_id` the chat tab (`None` for the settings agent). A composer recording uses the same recorder (`start_composer_recording` → `start_recording`), so one recording at a time holds for all. Every pill start sets the owner back to `Pill`.
- **Commands** (`commands/speech.rs`, async, the owner is the calling webview; JS parameter `tabId`): `start_composer_dictation(tabId?)` is refused with `SpeechError::Busy` (message names what records: "The recording pill is already in use", "Dictation is already running in Chat" / "Settings") while `busy()` is not `None`, drops a held recording of the same window and spawns a session-scoped level task (every `TICK` 50 ms: `tail_rms`, `level_from_rms`, `smooth_level`, as the pill's). `finish_composer_dictation()` (owner only, `NotRecording` otherwise) stops: under `MIN_RECORDING_SAMPLES_SECS` (or no samples) it emits an empty transcript; else it encodes the WAV, sets `is_transcribing` in the same lock as the stop (so the busy state never drops between), and a background task emits `composer-dictation-transcribing`, transcribes with `transcribe_with_retry` (the configured automatic attempts, no `on_retry` events) and emits `composer-dictation-transcript`; `NoSpeechDetected` is an empty transcript. A failure keeps the WAV in memory under the window label and emits `composer-dictation-error`. `cancel_composer_dictation()` (owner only, no-op otherwise): recording → `cancel_recording`, audio discarded; transcribing → the abort of `retry_abort` fires; also drops the held WAV. `retry_composer_dictation()` re-transcribes the held WAV of the calling window (same events from `composer-dictation-transcribing` on), refused with `Busy` while `busy()` is not `None`, `AudioUnavailable` without one. `dismiss_composer_dictation()` drops the held WAV. `get_dictation_busy()` returns the busy state.
- **Events** — all to the owner window only (`emit_to(label)`), none app-wide except `dictation-busy-changed`. See "Events".
- **Session identity** — a transcription is tied to `SpeechService::session` (a held-WAV retry bumps it): the result of a cancelled transcription that arrives after a newer session started is dropped (`owns_composer_transcription`), so it neither emits nor holds nor frees the newer session.
- **Held WAV** — one per window label, in memory only (lost at quit, never on disk), until Retry, Dismiss, a cancel, a new start of the same window or the owner end. At most one per window, so two in memory at most.
- **Busy state** — `SpeechService::busy()`: `None` while neither recording nor transcribing, else `{ by: "pill" | "chat" | "settings" }`. The app-wide event `dictation-busy-changed` carries the same payload (`null` when idle) after every change: pill start, end of the pill's transcription on every path (`end_transcription`, `abort_transcription`, the no-speech arm), pill cancel, composer start, end and cancel. Recording → transcribing keeps the same value and emits nothing.
- **Guard and warning** — `SpeechService::composer_window()` is the one guard: `Some("Chat" | "Settings")` while a composer records or transcribes. `toggle_speech_recording` (so the hotkey, the context menu "Speech to Text", Shift+click on a skill, the GNOME widget actions), `stop_chat_speech_recording`, `cancel_speech_recording`, `pause_speech_recording` and `resume_speech_recording` ask it first, start or stop nothing and show the warning toast "Dictation is running in Chat" (or "Settings"; event `speech_recording_start`, title only, `session.rs` `warn_composer_running`).
- **Owner end** — `ai_webview::hide_host` cancels the session owned by `conversation-dialog` and the `Destroyed` handler in `services/dialog.rs` the one owned by `settings-dialog` (`composer::cancel_owned_by`): recording or transcription ends, audio and held WAV are dropped, no history entry. `hide_host` also calls `capture::cancel_owned_by`, which ends a running chat screenshot or select-text capture (see "Capture owners"). Every cancel of a recording or transcription (command or owner end) emits `composer-dictation-cancelled { tabId }`, so a hidden chat page resets its composer.
- **Not available** — no pause in composer dictation; the settings agent has no pill path any more (no pill target, no `settings-agent-dictation` event).
